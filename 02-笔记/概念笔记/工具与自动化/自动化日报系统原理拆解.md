# 自动化日报系统的技术原理拆解

> 从"读新闻"到"AI 自动筛选 + 推送到手机"——拆解这套系统背后所有值得理解的技术原理

---

## 1. 为什么 GitHub Actions 可以做定时任务？

### 传统方案 vs GitHub Actions

| 需求 | 传统方案 | GitHub Actions |
|------|---------|---------------|
| 需要一台一直开着的机器 | ✅ 服务器 / VPS | ❌ 不需要 |
| 需要配置定时触发 | `crontab -e` | `.github/workflows/*.yml` + cron |
| 需要存储/执行代码 | 手动部署 | Push 到 GitHub 自动同步 |
| 需要网络访问权限 | 自行解决 | GitHub 自带网络 |

**核心原理**: GitHub Actions 的本质是 **GitHub 替你跑一个 Docker 容器**，你只需要告诉它：
- **什么时候跑** → cron 表达式
- **跑什么** → `run:` 后面的 shell 命令
- **用什么跑** → `runs-on:` 指定的操作系统

### Cron 表达式

```
0 22 * * *
┬ ┬ ┬ ┬ ┬
│ │ │ │ └── 星期 (0-7, 0和7=周日)
│ │ │ └──── 月份 (1-12)
│ │ └────── 日期 (1-31)
│ └──────── 小时 (0-23) ← UTC 时间
└────────── 分钟 (0-59)
```

> **时区陷阱**: GitHub Actions 的 cron 用的是 **UTC 时间**。北京时间 = UTC+8，所以要北京时间 6:00 AM 跑，就要设 `0 22 * * *`（UTC 22:00 = 北京 6:00）

### 为什么它免费？

GitHub Actions 对**公开仓库**提供免费额度（每月 2000 分钟）。Horizon 是 MIT 开源协议，你的仓库也是公开的，所以每天的 3-5 分钟运行时间完全在免费额度内。

### 局限
- 单次运行最长 **6 小时**（对我们够了，日报只需几分钟）
- 没有公网 IP（不需要，因为我们只往外推，不等人来访问）
- 工作目录每次从头拉代码（所以要用 `uv sync` 装依赖）

## 2. Webhook：一条 HTTP POST 消息的旅程

### 什么是 Webhook？

> Webhook = **反向 API**：不是你主动去问，而是有消息时系统主动告诉你

```
传统 API:  你 → 问服务器 → 服务器返回数据
Webhook:   服务器有消息 → POST 到你给的 URL → 你收到通知
```

### Horizon → 飞书的 Webhook 流程

```
Horizon 生成日报 Markdown
       ↓
将 Markdown 包装成飞书的"消息卡片"格式 (JSON)
       ↓
发起 HTTP POST 请求，发到飞书机器人 URL
       ↓
飞书服务器解析卡片 JSON，在你的群里展示
```

### 飞书消息卡片的 JSON 结构

```json
{
  "msg_type": "interactive",      // 消息类型：交互式卡片
  "card": {
    "schema": "2.0",              // 卡片版本
    "header": {
      "title": {"tag": "plain_text", "content": "Horizon 日报"},
      "template": "blue"          // 头部颜色
    },
    "body": {
      "elements": [               // 正文元素列表
        {"tag": "markdown", "content": "# 新闻内容..."}
      ]
    }
  }
}
```

这个 `msg_type: interactive` 就是飞书**自定义机器人**的"花式消息"——不是纯文本，而是带有格式的富文本卡片。

### 三种常见推送平台对比

| 平台 | 机器人类型 | 消息格式 | 复杂度 |
|------|-----------|---------|--------|
| **飞书** | 群自定义机器人 | Interactive Card JSON | ⭐⭐ |
| **钉钉** | 群自定义机器人 | Markdown / ActionCard | ⭐⭐ |
| **Slack** | Incoming Webhook | Block Kit JSON | ⭐⭐⭐ |
| **Discord** | Webhook | Embed JSON | ⭐⭐ |
| **QQ** | ❌ 没有自定义机器人 | — | ❌ |

> QQ 是唯一没有"自定义机器人 webhook"的主流 IM——这也是为什么我们需要跑 Lagrange.OneBot 这种外部框架。

## 3. 从 GitHub → 飞书的完整数据流

```
 你 Push 代码到 GitHub
       ↓
 GitHub Actions 检测到 .github/workflows/daily-summary.yml
       ↓
 每天 UTC 22:00 触发（北京时间 6:00）
       ↓
 GitHub Actions Runner 启动 Ubuntu 容器
       ↓
    1. checkout 拉代码
    2. setup-python 装 Python
    3. setup-uv 装 uv
    4. cp data/config.github.json data/config.json
    5. uv sync 装依赖
       ↓
    uv run horizon --hours 24
       ↓
    抓取器并发工作： ─┬─ RSS
                      ├─ HackerNews
                      ├─ Reddit
                      ├─ GitHub
                      ├─ GDELT / Google News
                      └─ OSSInsight
       ↓
    所有原始内容去重合并
       ↓
    DeepSeek API 逐条打分（0-10）
       ↓
    过滤掉低分内容（< 5.5 分）
       ↓
    对高分内容补充背景知识（AI 第二次调用）
       ↓
    生成中文日报 Markdown
       ↓
    POST 到飞书 Webhook URL → 群里收到卡片
       ↓
    同时存到 data/summaries/ + 推送到 GitHub Pages
```

### 关键知识点 1：环境变量与密钥安全

```yaml
# .github/workflows/daily-summary.yml 中
env:
  DEEPSEEK_API_KEY: ${{ secrets.DEEPSEEK_API_KEY }}
```

- **永远不要把密钥写在代码里**
- GitHub Secrets 会将密钥加密存储，只有 GitHub Actions 运行时才能解密
- `.env` 文件在 `.gitignore` 中，不会被提交到仓库
- 本地开发用 `.env`，线上用 GitHub Secrets → 同一个环境变量名

### 关键知识点 2：双配置文件策略

```
config.json          ← 本地开发用（.gitignore 忽略）
config.github.json   ← GitHub Actions 用（提交到仓库）
```

工作流里用 `cp data/config.github.json data/config.json` 来切换。这样本地配置和线上配置可以不同（比如本地日志级别更详细，线上更安静）。

## 4. 代理与网络：调试踩坑实录

### 问题 1：Hosts 文件优先级高于 DNS

```
# 在 C:\Windows\System32\drivers\etc\hosts 中
140.82.112.3    github.com     ← 强制指向旧 IP
```

- Hosts 文件的 DNS 解析**优先级最高**，会直接覆盖 DNS 查询结果
- 即使用了代理，如果 hosts 写死了某个 IP，还是会连那个 IP
- 修复：注释掉或删除这些行，`ipconfig /flushdns` 清缓存

### 问题 2：代理的不同层级

```
系统代理 (System Proxy)     ← 浏览器、大多数应用使用
    ↓ 指向
代理客户端 (FlClash)        ← 监听 127.0.0.1:7890
    ↓ 连接
远端代理服务器              ← 机场/自建节点
```

- **系统代理**（Windows 设置中的"代理服务器"）告诉浏览器："把流量发到 127.0.0.1:7890"
- **代理客户端**（FlClash）接收流量，根据规则决定"直连"还是"走远端"
- **Git 代理**（git config http.proxy）是独立的，不跟随系统代理

### 问题 3：容器/沙箱环境中 127.0.0.1 指向的是容器自己

```
沙箱内 127.0.0.1:7890 → 沙箱自己的 7890 端口（未必有服务）
宿主机 127.0.0.1:7890 → 宿主机的 FlClash（有服务）
```

这两个是不同的网络命名空间。所以从沙箱里连 `127.0.0.1:7890` 连不上宿主机的代理。

## 5. FlClash 配置的坑

### 配置文件结构

```
FlClash GUI (FlClash.exe)
    ↓ 管理
订阅/配置文件（如 魔戒.net）
    ↓ 写入
运行时配置 (~/.config/ssyun/config.yaml)  ← FlClashCore 真正读的
    ↓ 加载
Mihomo 核心（FlClashCore.exe） ← 负责实际代理
```

### 踩坑点

- **`proxies: []` 是空的，所有流量直连** → 梯子"开了但没完全开"
- **修改配置后要重启 FlClashCore** 才能生效
- **YAML 格式问题**: Python 的 `yaml.dump()` 可能会破坏原有格式，导致核心无法解析
- **规则过多的性能问题**: 3877 条规则 + 完整 DNS 配置可能导致核心启动卡死

## 6. 用 uv 做 Python 项目管理的优势

为什么 Horizon 用 `uv` 而不是 `pip`：

| 特性 | pip | uv |
|------|-----|----|
| 安装速度 | 串行下载 | **并行**下载，快 10-100x |
| 依赖解析 | 慢（resolver） | **Rust 实现**，快 100x |
| 锁文件 | 需要第三方工具 | 原生 `uv.lock` |
| 虚拟环境 | `python -m venv` | `uv venv` |
| 多 Python 版本 | pyenv + pip | 内置 `uv python install` |

## 7. 目录链接：junction / symlink

为了让 Horizon 生成的日报直接出现在 Obsidian 知识库里，我们用了 **junction**（目录链接）：

```powershell
# 语法：mklink /J 链接目录 目标目录
mklink /J "E:\code\MizukiBot\components\Horizon\summaries" "E:\code\知识库\Horizon 日报\日报存档"
```

- `mklink /J` 创建 Windows 的目录链接（类似 Linux 的 `ln -s`）
- 写入链接目录 = 写入目标目录
- Horizon 往 `summaries/` 写 = 直接写到了知识库的日报存档文件夹
- 不需要复制文件，不需要额外步骤
